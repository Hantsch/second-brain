From the 2026-09-03 architecture review ([finding 3.6-2](../reviews/2026-09-03-architecture-review.md)),
P2. Evidence: `.pdf` is classified but not read — the file is copied with a `pdf-not-read` note
(`src/core/ingest/file.ts:48`, `:113`), lands as `text: ''`, and the job ends `awaiting-llm`,
permanently undigestable. The deliberate no-heavy-parsers rationale is documented at
`src/core/ingest/file.ts:8`.

## Requirement

The knowledge pillar is "YouTube and articles" — and after web pages, the most common form an
article takes is a PDF: papers, whitepapers, documentation exports, invoices worth keeping. Today
a PDF is copied into `raw/` and then sits there forever as an undigestable source; the pipeline
cannot extract its text, and the "awaiting" state it lands in never resolves.

A text-based PDF should yield its text to the same pipeline every other source uses: extracted
into the raw folder alongside the original, digestible into a module, citable. Scanned/image
PDFs without a text layer are out — OCR is its own concept; the honest note for those stays. The
existing no-native-modules constraint holds: whatever extracts the text must be pure JS.

## Acceptance Criteria

- [x] Ingesting a text-based PDF produces extracted text in the raw folder next to the
      untouched original, and the source is digestible like any text source.
- [x] A PDF without a text layer (scanned) ends in an honest, named state — distinct from "no
      model configured" — with the original still preserved.
- [x] The 5 MB-class size guard applies; an oversized PDF fails visibly, not silently.
- [x] No native module enters the dependency tree.
- [x] Tests cover: a text PDF, a scanned PDF, an oversized PDF — none touching the network.

## Open Questions

## Decisions (Sprint)

- **Library: `unpdf`** (serverless pdf.js build, zero runtime dependencies; `@napi-rs/canvas` is
  only an _optional peer_, which npm does not install) — `pdfjs-dist` pulls `@napi-rs/canvas` in
  as an optionalDependency (a native binary) and `pdf-parse` wraps an old, unmaintained pdf.js.
- **Loaded by dynamic `await import('unpdf')`**, mirroring `src/core/ingest/youtube/innertube-client.ts:44`,
  because main is built as CJS (`electron.vite.config.ts`) and `unpdf` is ESM-only.
- **Extraction is a plain core function (`src/core/ingest/pdf.ts`), not a new interface** — the
  swappable seam is already `SourceIngestor`; PDF parsing is an internal detail of the file ingestor.
- **Bytes come through a new `IngestFileSystem.readBytes`** — core never touches `node:fs`
  directly, and the fake file system stays the test seam.
- **"No text layer" = the extracted text of all pages trims to empty** → new note
  `pdf-no-text-layer`; the queue's existing empty-text rule (`queue.ts` `condense`) then ends the job
  `no-content` with that note as its message, which is already distinct from `awaiting-llm`.
- **A PDF pdf.js cannot open (damaged, password-protected) keeps the `pdf-not-read` note**, reworded
  to say so — the original is stored either way, and the note is honest instead of a crash.
- **Size guard: a PDF larger than `MAX_TEXT_BYTES` (5 MB) throws `IngestError('too-large')` before
  anything is written** — a binary cannot be truncated the way text is, and an error stage is the
  visible failure the AC asks for; `too-large` becomes a known error code (core, IPC, i18n).
- **Extracted text goes to `source.md` next to the original** with the same frontmatter the HTML
  case writes, pages separated by a blank line — one text file per raw folder, as for HTML.
- **Title stays the file name** — PDF metadata titles are routinely junk
  ("Microsoft Word - draft3.docx"), and the file-name rule is what every other file uses.
- **Test PDFs are generated by a small TS builder in `tests/fixtures/pdf/`, not committed binaries**
  — readable, deterministic, and usable from both Vitest and Playwright.
- **"No native module" is proven by a test over `package-lock.json`**: no non-dev package may carry
  `hasInstallScript`, `gypfile`, `os`/`cpu` constraints or a `@napi-rs/*`/`canvas` name — the same
  markers every prebuilt/native package carries.
- **The e2e spec routes the fake provider** (as `url-no-content.spec.ts` does), so a text PDF reaches
  `done` — "digestible like any text source" proven end to end, not just "not empty".
- **Story preface correction:** since 051 an unread PDF ends `no-content`, not `awaiting-llm`
  (`queue.ts:303`); the plan builds on the current behaviour.

## Plan

1. Add `unpdf` as a runtime dependency and a lockfile test that no native package is in the
   production tree (D1).
2. `src/core/ingest/pdf.ts`: `extractPdfText(bytes)` → `{ kind: 'text', text, pages }` |
   `{ kind: 'no-text-layer', pages }` | `{ kind: 'unreadable' }`; plus a PDF builder for tests (D2).
3. Wire it into `src/core/ingest/file.ts`: read bytes, write `source.md`, provenance `file` for a
   text PDF; note `pdf-no-text-layer` / `pdf-not-read` otherwise; original always copied (D3).
4. Size guard with the new `too-large` error code through core, `IpcError` and `KNOWN_ERROR_CODES` (D4).
5. Renderer strings (de/en) + `NOTE_CODES`, and one e2e spec driving all three cases through the
   inbox (D5).

Order: D1 → D2 → D3 → D4 → D5. No renderer layout change; only strings.
